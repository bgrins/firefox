The two guards implement a defensible conservative **readiness condition**, not a complete native correctness argument. They prevent Round/ModRem from treating unresolved relative coefficients or hinted percentages as resolved magnitudes. The five Lean claims replay, with both false controls rejected. The candidate remains unsuitable for independent acceptance until deferred consumers and the existing runtime Round arithmetic discrepancy are handled. This review changes no native source, index, epoch, build, or browser.

### Knowledge contract

`CalcNodeLeaf::canonical_value` promises a value in the type's canonical unit when sufficient information exists. Specified absolute lengths convert to px; number, angle, time and resolution have known values. Relative lengths return None. A percentage returns Some only with the Percent hint: it is then a raw percentage, rather than a coefficient awaiting another basis. Computed lengths are px, but computed percentages with a different hint still return None. Fixed random keys may resolve; other keys, tree-counting and unresolved color channels do not provide canonical knowledge at the specified stage.

Consequently, `unitless_value`, same leaf discriminant, same relative unit, positive coefficient, or syntactic leaf status alone cannot replace the guard. A zero, negative, infinite or underflowing eventual basis can change the operation's domain/classification. Requiring both canonical values is sufficient to establish this *knowledge fact under the trait implementations*, provided the children and type checking are valid. It is not sufficient to establish the result of the subsequent arithmetic or the consumer's ability to retain the tree.

The guard is deliberately stronger than logical necessity. A known canonical zero step determines NaN even if the value is unknown; some symbolic identities could admit other safe deductions. Such optimizations need their own result-construction and dependency argument. In particular, `coerce_to_value` on an unresolved tree is not a justified replacement by a typed constant. Keep the conservative guard unless an optimization has an explicit proof and tests.

`Some` includes NaN and infinities. It must not be interpreted as finite/nonzero. The special branches still need their own ordering. Canonical readiness is also not a promise that an arbitrary caller of the direct-children method has canonicalized the actual stored leaf: normal whole-tree simplification visits children and specified Leaf::simplify normalizes absolute units first. Preserve that caller invariant, or classify the returned canonical scalars directly in a future shared evaluator.

### Every Round branch

1. **Zero step:** the guard now blocks unresolved zero coefficients. A relative zero coefficient is not sufficient domain knowledge in every nonfinite context. With resolved zero, the existing typed NaN result remains appropriate.
2. **Both infinite / infinite value:** nonleaf or relative operands can no longer trigger an early infinity conclusion. Known NaN must take priority over infinity; the accepted runtime path has this check, while the existing simplifier does not have an equivalent explicit NaN-first check. That pre-existing distinction is documented in the prior special-knowledge audit; these two guards do not repair it.
3. **Infinite step:** sign/zero-dependent outputs run only for known leaf operands. Preserve all four strategies and signed zeros. The guard covers the earlier unknown-expression/unknown-basis cases; do not award them another independent count.
4. **Negative step:** negation occurs only after readiness, so coefficient sign is not used to infer an unresolved basis sign. Absolute-step semantics remain.
5. **Finite remainder and exact multiple:** the existing remainder calculation and exact-value return remain byte-identical. They are no longer executed early for unresolved relative operands.
6. **Finite bounds:** negative upper-zero preservation, lower/upper construction, upward ties, and to-zero magnitude selection remain intact in the simplifier. A deferred expression may instead reach the different runtime branch discussed below.
7. **ModRem:** both early and deferred operations use `ModRemOp::apply`. Its finite remainder, signed-zero, and infinite-divisor behavior is unchanged. Keep its accepted controls; a proof of guard readiness does not reprove those f32 operations.

### Different stages need different preservation checks

The current length-percentage pipeline maps contextual length leaves with `to_computed_value_for_math`, then calls `LengthPercentage::new_calc`, which simplifies again. A plain `width: round(...em...)` therefore does not justify claiming that the runtime quotient branch is reached. Hinted percentages remain deferred through this pass; `CalcLengthPercentage::resolve` supplies the actual layout basis through `resolve_map` before numeric resolution. The zero-basis defect applies to these percentages too, while raw opacity percentages have a different readiness contract.

`CalcNumeric::resolve` instead maps leaves through `to_computed_value(Some(context), None)` and calls `resolve()` directly. It does not run another simplification pass. Its runtime Round computes a binary32 quotient followed by floor/ceil. The known `css-round-context-quotient-*` investigation already demonstrates why this is not equivalent to the simplifier's finite remainder selection. This is **the same existing family**, not a new bug or acceptance count. The prior prospective repair uses a wider remainder-based reconstruction; copying the f32 simplifier wholesale is not justified because that earlier work records additional one-ULP problems with the first f32 reconstruction attempt.

A concrete guard-exposure candidate is `opacity: sign(round(down, 1em, 0.3333333432674407958984375em) - 0.8px)` at a computed 1px font. Before the guard, the inner same-unit Round can fold to approximately 0.6667em. After the guard, the retained numeric tree can resolve Round to 1px because the stored step 0x3eaaaaab makes the binary32 quotient round to 3. The sign/opacity result can consequently change from 0 to 1. This exact browser route has **not** been executed by this review. `KNOWN-QUOTIENT-REPLAY.json` independently reruns the existing two-pair Fraction/binary32 witness; it is not a native execution. Do not use a plain width example as evidence for this route.

The typed consumer review independently reports parse-time `resolve(Some)` requirements in Steps, Bezier coefficients and linear() outputs. Steps/Bezier fields can retain ASTs, but current linear() storage is already scalar. A coherent repair must retain selected specified expressions where required, evaluate them in the correct owner context, and preserve dependencies/invalidation and APIs lacking an owning style. A type whitelist, Unknown-as-zero, or broad parser rejection does not solve that contract. The separate linear second-endpoint panic lead is not caused by this stepped patch and is outside this review.

### Minimal corrective direction and gates

Keep the two readiness guards and leave general coefficient addition/multiplication helpers alone. Before treating the result as landable, carry the already-reviewed Round scalar semantics through the deferred numeric path, including accepted runtime NaN priority and signed-zero preservation. Prefer one reviewed scalar operation after canonical/type resolution to two drifting implementations, but do not replace existing branches merely on that design preference. Reconcile the held quotient repair against this exact base and preserve its existing controls.

Add bounded controls for: all four Round strategies; ±zero, ±infinity and NaN in both positions; negative steps; exact multiples and upward ties; absolute-unit normalization; em/rem/cq bases positive→zero→positive; hinted percentage bases positive→zero→positive and a raw-percentage control; the known context-quotient witness through CalcNumeric; and ordinary Steps/Bezier/linear admission and owner-context mutation. Keep the accepted division/cancellation/zero-product controls. Consumer corrections need their own actual compiled/runtime verification; unchanged source bodies alone do not establish preservation.
