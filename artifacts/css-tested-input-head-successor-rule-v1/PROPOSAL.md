# Permit proven HEAD successors without rebuilding runner packages

Use one small shared predicate returning an immutable evidence record: `verify_head_successor(anchor, current, role, protected_inputs, publication_receipt=None)`. Replace only the fixed-HEAD equality gates. Keep the existing externally supplied epoch hash, full current preservation check, compiled-role requirement, actual test/source/resource pins, BuildID/binary identity, application.ini link/target checks and cleanup guards. This is a design, not an implemented permission or a change to the imminent v5 experiment.

## Default rule: artifact-only descendant

Require the anchor and current commits to be available and the intervening history to be a linear descendant chain. Inspect the actual parent/child Git tree changes of every commit, with rename detection disabled; reject merges, mode/type changes, renames, gitlinks and any non-artifact path change. Authenticate the signed commit receipts/signatures under the existing local signing policy. Checking only an endpoint diff would conceal intervening changes and is insufficient.

Allow additions of regular files in new research directories that are not executable-input/package roots, and the two established ledger files only when their exact before/after bodies are authorized by the preserved signing/epoch update receipts. Existing pinned artifacts, executed helpers and manifests remain immutable. Reject additions inside a protected package (including potential import shadowing), mutation of old evidence, or nested-repository changes. A blanket `artifacts/` exemption is too broad: artifacts contain the running tools, tests and proof packages.

Verify the entire tracked non-artifact tree projection is unchanged, not just the two candidate Rust files. Independently revalidate all actual working source/build configuration, runtime, test/metadata/resource and environment pins required by the selected role; preserve the complete untracked companions and nested state. The original/candidate roles may have their explicitly authorized source/binary differences, but each role must still match its own authenticated build and experiment contract. An incomplete source/build receipt cannot be repaired merely by proving an artifact-only Git diff.

A current epoch is still explicit and externally hash-bound. The existing signing helper already produces a new epoch after each commit; the successor record joins that epoch to the immutable tested epoch and accounts for only HEAD/index and authorized research/ledger bookkeeping changes. Do not silently add changed operational inputs to the accepted pin set. Return the anchor/current commits, inspected commit/tree deltas, signed receipt hashes, tested epoch/evidence hashes and current protected-input hashes. Runners can use the unchanged package with this record on each invocation; no per-commit package version is needed.

## Separate exception: publishing an already-tested working candidate

A native publication changes HEAD's blobs while leaving the actual working and compiled candidate bodies unchanged. This is not artifact-only. Permit it only via an explicit signed publication receipt identifying the exact commit, parent, three paths, old/new blob hashes and modes. For this repair those paths are the two native candidate files and the new A WPT. Require the native preimages to match the original role, native postimages to equal the tested working candidate, and the added WPT to be byte-identical to the tested capsule fixture. No other non-artifact tree change is allowed. Its research ancestors and later research descendants must satisfy the default rule.

Verify that current working source/configuration/runtime hashes still match the tested candidate/build receipt, the installed WPT matches the tested fixture, and the commit signature/tree/parent are exact. The expected two native dirty paths become clean; update that accounting explicitly instead of weakening dirty-tree checks. Keep the original role's base hashes as historical data and use the publication's candidate blobs as the new HEAD expectation for restoration. This exception is valid for reusing candidate evidence or restoring that candidate's prototypes; it does not turn the published tree into an original baseline and cannot validate new native edits. WPT installation may occur after the isolated capsule run, but needs its own absent-to-owned-regular-file receipt and proof of identical tested bytes.

## Provenance stays separate from equivalence

Never rewrite an old receipt's revision, epoch hash, BuildID or run timestamp. Record `tested_checkout_head`, `current_checkout_head`, the build receipt and successor relation separately. The existing `application_metadata(..., epoch_head)` function sets its `revision` field from the checkout epoch; it is not evidence that this revision was embedded in the binary. Preserve that legacy field in old receipts and label new checkout/build provenance explicitly. A new build or test/resource change still requires actual validation; publication and research commits are not new executions. Native acceptance and prototype certification remain separate ledger decisions.

## Small guard changes when implemented

- WPT `run.py::main`: replace frozen-current and original/current revision equalities with the successor predicate; keep source-role checks and strict original-evidence adoption. Keep BuildID, normal binaries, application metadata and epoch checks intact.
- Sign observer `run.py::main` and `adoption.py::validate`: join evidence through the same authenticated successor record, rather than requiring identical checkout revision strings. The same-run normative/observer binary, source and metadata identity still must hold; cross-commit evidence reuse requires the explicit relation.
- Source transition `verify_wpt` and main preflight: accept a tested-to-current epoch relation instead of exact historical/current epoch equality. Derive HEAD blob and dirty-set expectations from the explicit publication receipt only in that mode. Preserve full source ownership, rollback, index/nested, regular-file and 140 recovery-pin checks.
- Leave `epoch.py::verify_current` strict and unchanged. It validates the current state, while the new predicate relates two already authenticated states.

Focused negative controls should reject a one-byte pinned-helper edit, package import-shadow addition, native edit then revert in an intervening commit, wrong build/fixture bytes, omitted publication path, publication of prototype bodies, altered ledger history, merge/reparenting, and using published candidate evidence as an original observation. Positive controls are an ordinary signed new research-directory commit and the exact three-path publication with unchanged tested candidate inputs.
