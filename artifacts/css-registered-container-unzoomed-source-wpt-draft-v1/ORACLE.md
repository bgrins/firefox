# Registered container lengths from unzoomed sources

**Question:** Do registered physical container lengths retain canonical computed values when only the consuming target is zoomed, and do unzoomed per-axis selection and viewport fallback remain correct?

**Scenario:** Every source container and its ancestors have CSS zoom1, fixed content-box dimensions, no padding, borders or transforms. Targets are absolute siblings and cannot resize their sources. All writing modes are horizontal-tb and remain unchanged. Each test has its own fixed320x180 iframe. The target zoom changes1→2→.5→1. Registrations are non-inherited `<length>` with initial7px. Direct and ready unregistered-provider substitution paths are separate tests; the fallback is7px, avoiding an unrelated unused relative-unit dependency.

This manual trace uses the official2026-10-27 captures pinned in REFERENCES.json. webspec-index was unavailable in the existing investigation; anchors were rechecked directly in the captured HTML. No exhaustive automated route enumeration or fresh web fetch is claimed.

1. [Registered computed values](https://drafts.css-houdini.org/css-properties-values-api-1/#calculation-of-computed-values) parse the selected value as a length and convert its unit to the canonical length unit. The ready provider supplies exactly100 of the tested unit; its fallback is unused.
2. [Container lengths](https://drafts.csswg.org/css-conditional-5/#container-lengths) select the nearest eligible ancestor separately for each relevant axis. The size features use that container's content-box dimensions. Every source has effective zoom1 here, so the contested non-unit source zoom conversion is the identity under either convention.
3. The single size container gives cqw/cqh=200/120px, then300/150px, then200/120px. In the merged case the nearest horizontal inline-size container supplies width, while the outer size container supplies height:200/180px, then140/220px, then200/180px. cqmin/cqmax take the smaller/larger of those two axes; their ordering swaps in the middle state. No target writing-mode change is involved.
4. When neither ancestor accepts a size query, the same container-length section explicitly selects the small viewport size on the missing axis. In this fixed iframe100cqw/100cqh therefore become320/180px, independently calibrated by100svw/100svh controls.
5. [Registered substitution](https://drafts.css-houdini.org/css-properties-values-api-1/#substitution) supplies the computed registered length to width. [Viewport CSSOM](https://drafts.csswg.org/css-viewport/#zoom-om) distinguishes unscaled computed length output from scaled bounding rectangles. With unzoomed ancestors, the registered property and consuming width remain the expected pixel value, while target rectangle width is that value times target zoom. The independently specified literal-pixel sibling must show the same bounded behavior.

**Verdict: REACHED** for these unzoomed-source cases and the specified viewport fallback. They do not establish how a source with effective zoom other than1 should be normalized. The earlier cross-zoom-source trace remains INCONCLUSIVE. Ordinary Firefox cqw/cqh output is not used as an oracle, because that path has a known zoom issue. The literal controls and svw/svh fallback controls are intentionally independent of it.
