Three distinct gaps need separate treatment. A leaf-only guard addresses the destructive non-leaf simplifications, but is not a complete special-value repair. Neither a coefficient predicate nor deferral by itself establishes correct runtime semantics.

**Unknown expression operands.** Generic `is_infinite_leaf`, `is_negative_leaf` and `is_zero_leaf` return false for non-leaves. In the Round simplifier, an infinite value therefore survives an unknown step even when the eventual step is zero, infinity or NaN. Conversely an infinite step selects a result from false negative/zero tests on an unknown value. `coerce_to_value` maps a tree's leaves; it does not replace a nonlinear tree with a constant. The prior audit already explains the observed both-infinite case. This audit adds source-backed dual-step candidates, without claiming new browser reproduction.

A minimal structural guard at the start of the Round arm would require both `value.as_leaf()` and `step.as_leaf()` before any special-case mutation. This leaves existing leaf arithmetic and fix13's signed-zero branches unchanged and does not touch the finite quotient candidate in `resolve_internal`. It avoids recursively coercing unknown trees and discarding an unknown step. It remains only a partial proposal: the two other gaps below survive it. Do not change the global helper predicates to return errors for all non-leaves without auditing their other callers.

**Context-dependent leaf magnitudes.** Both specified and computed CalcNodeLeaf implementations inherit predicates based on `unitless_value`. Specified lengths supply raw unit coefficients; `canonical_value` returns None for contextual lengths and unresolved percentages. Thus a finite nonzero em coefficient can become zero, and an infinite em coefficient can become NaN at font size zero. Positive basis alone is also insufficient as a universal machine contract because conversion can underflow or overflow; percentage hints can additionally permit sign-changing bases. Requiring only syntactic leaves does not close these cases.

For a general correct folding policy, defer Round whenever either operand lacks a resolved canonical value, and evaluate the special classification from those canonical values. Keep the finite arithmetic implementation and signed-zero rules separately reviewed. A more permissive optimization needs an explicit semantic invariant for the entire possible value class, not a raw-coefficient test. For example, dropping Round around an infinite value requires the step to be known finite, nonzero and non-NaN. A known zero step could permit an unconditional typed NaN result, but constructing that result must not recursively remap an unresolved operand tree.

That broader canonical-value policy is not presented here as a drop-in patch. Deferring previously folded contextual expressions can change context-free `Integer::resolve` admission, the same integration class identified while holding fix120. Computed percentages can remain unresolved as well. Such callers and the timing of re-simplification need explicit coverage before adoption. Even ordinary same-unit finite rounding at a zero basis can change an apparent nonzero step into zero; that finite-folding issue is outside the observed unknown-tree witness and should not be silently folded into its acceptance.

**Runtime NaN propagation.** `resolve_internal` first resolves both operands, but its special branches omit an explicit NaN check. With infinite value and NaN step it returns the infinity; with NaN value and infinite step it can return zero or infinity. Therefore simply deferring a contextual NaN can still produce the wrong result. The simplifier also needs equivalent NaN priority for known canonical operands. The prospective runtime operation is a NaN check before zero/infinity selection; NaN must remain an intermediate value until the normal top-level boundary. This is distinct from finite quotient precision.
