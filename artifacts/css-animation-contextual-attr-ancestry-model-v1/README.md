# Guard ancestry and cached attribute results

This isolated Lean model rejects context-only result reuse even when the evaluator checks the current physical guard before consulting its cache. It also shows that an immediate parent name plus request/occurrence label is insufficient. A parent invocation identity can be justified by showing that it determines relevant ancestry (or equivalent reference outcomes); merely reusing the parent's context key does not establish that property. No native correctness or canonical coverage is claimed.

The reference evaluator is a pure six-request program. Two requests share physical attribute A: one returns input7, another invokes the first while A is active. A separate chain is Parent→ReadD→LeafD, with an optional outer RootD sharing LeafD's physical attribute. A guard check precedes evaluating each body. The reference evaluator neither reads nor mutates a cache. The memo evaluator independently implements guard-first lookup, recursive body evaluation and shared cached outcomes. Cycle and fuel exhaustion are distinct results; there is no fallback/defaulting or CSS parser in this model.

A sixth theorem states the conditional identity obligation directly: if equal invocation identities imply equal ancestry, reference outcomes agree for fixed request, input and fuel. A recursively fresh parent/occurrence path can satisfy this premise; this model does not establish that the prototype's pointer/parent IDs do so. Physical guard identity still has to remain independent of the contextual request identity. A larger SCC/session key is not proved universally necessary: the missing obligation is that cached results refer to the same relevant guard history and unchanged resolved inputs, or that invalidated entries are discarded. In-progress SCC defaulting, custom guards, parser context, attr types and policy changes remain outside the six-request abstraction.
