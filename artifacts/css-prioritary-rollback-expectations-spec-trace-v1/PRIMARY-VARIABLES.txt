L387: Note: That is, var(--a,) is a valid function, specifying that if the --a custom property is invalid or missing, the 【55†var()】 should be replaced with nothing.
L388: 
L389: Note: The syntax of the fallback, like that of 【54†custom properties】, allows commas. For example, var(--foo, red, blue) defines a fallback of red, blue; that is, anything between the first comma and the end of the function is considered a fallback value.
L390: The fallback value allows for some types of defensive coding. For example, an author may create a component intended to be included in a larger application, and use variables to style it so that it’s easy for the author of the larger application to theme the component to match the rest of the app.
L391: Without fallback, the app author must supply a value for every variable that your component uses. With fallback, the component author can supply defaults, so the app author only needs to supply values for the variables they wish to override.
L392: 
L393:     /* In the component's style: */
L394:     .component .header {
L395:       color: var(--header-color, blue);
L396:     }
L397:     .component .text {
L398:       color: var(--text-color, black);
L399:     }
L400: 
L401:     /* In the larger application's style: */
L402:     .component {
L403:       --text-color: #080;
L404:       /* header-color isn't set,
L405:          and so remains blue,
L406:          the fallback value */
L407:     }
L408: To 【577†replace a var() function】, given a list of `arguments`:
L409: 
L410:   1. Let `el` be the element that the style containing the 【55†var()】 function is being applied to. Let `first arg` be the first 【63†<declaration-value>】 in `arguments`. Let `second arg` be the <declaration-value>? passed after the comma, or null if there was no comma.
L411:   2. 【61†Substitute arbitrary substitution functions】 in `first arg`, then 【578†parse】 it as a 【276†<custom-property-name>】. If parsing returned a <custom-property-name>, let `result` be the 【271†computed value】 of the corresponding 【54†custom property】 on `el`. Otherwise, let `result` be the 【66†guaranteed-invalid value】.
L412: 
L413: Note: Determining the 【271†computed value】 for the 【54†custom property】 implies that 【579†property replacement】 takes place, which may cause a 【580†cycle】.
L414:   3. If the 【54†custom property】 named by the 【55†var()】’s first argument is 【227†animation-tainted】, and the var() is being used in a property that is 【581†not animatable】, set `result` to the 【66†guaranteed-invalid value】.
L415: 
L416:   4. If `result` contains the 【66†guaranteed-invalid value】, and `second arg` was provided, set `result` to the result of 【61†substitute arbitrary substitution functions】 on `second arg`.
L417: 
L418:   5. Return `result`.
L419: Due to 【579†property replacement】, 【54†custom properties】 can form 【580†cycles】:
L420: 
L421:     :root {
L422:       --one: calc(var(--two) + 20px);
L423:       --two: calc(var(--one) - 20px);
L424:     }
L425: 
L426: 
L427: In the above, both --one and --two compute to the 【66†guaranteed-invalid value】, since their 【582†substitution contexts】 have been marked as cyclic.

L455: ### 4.1. Serializing Custom Properties
L456: 
L457: Custom property names must be serialized as the exact code point sequence provided by the author, including not altering the case.
L458: 
L459: Note: For non-custom properties, property names are restricted to the ASCII range and are 【108†ASCII case-insensitive†infra.spec.whatwg.org】, so implementations typically serialize the name lowercased.
L460: Specified values of 【54†custom properties】 must be serialized exactly as specified by the author (with one exception, below). Simplifications that might occur in other properties, such as dropping comments, normalizing whitespace, reserializing numeric tokens from their value, etc., must not occur.
L461: 
L462: Computed values of 【54†custom properties】 must similarly be serialized exactly as specified by the author (with the same one exception, below), save for the replacement of any 【55†var()】 functions.
L463: The one exception to serialization being precisely as specified in the source file is that an empty custom property (such as --foo:;) must serialize with a single space as its value.

L469: For example, given the following properties:
L470: 
L471:     --y: /* baz */;
L472:     --x: /* foo */ var(--y) /* bar */;
L473: 
L474: 
L475: the serialization of the specified value of --x must be `"/* foo */ var(--y) /* bar */"`, while the serialization of the computed value of --x must be `"/* foo */ /* baz */ /* bar */"`.
L476: 
L477: (Note that the leading whitespace on the value is automatically trimmed by the CSS parser; it’s not preserved here.)
L478: This "exactly as specified" requirement exists because authors sometimes store non-CSS information in custom properties, and "normalizing" this information can change it in ways that break author code.
L479: 
L480: For example, storing a UUID in a custom property, like --uuid: 12345678-12e3-8d9b-a456-426614174000, requires the UUID to be echoed back out as written when it’s accessed by script.
L481: This value is technically parsed by CSS as a series of adjacent numbers and dimensions. In particular, the segment "-12e3" parses as a number, equal to -12000. Reserializing it in that form, as required by CSSOM in other contexts, would fatally break the author’s use of the value.
L482: The requirement to serialize an empty custom property as a string with a single space in it instead is due to compatibility with the existing CSSOM API. `【616†setProperty()】` specifies that if the passed value is an empty string it instead acts as `【617†removeProperty()】`.
L483: This is a frankly weird behavior, and not something we would do in new APIs. But we can’t change the past, and letting empty properties accurately serialize as the empty string would mean that round-tripping a custom property value, or reading a property on one element and setting a property on another element to the same value, wouldn’t work as intended.
L484: Using a single space preserves the author-intended behavior as much as possible, while having the smallest chance of accidentally breaking things, since authors working with custom property values in JS are probably calling `【618†trim()†tc39.es】` on the values anyway.

L660: A renderer is conformant to this specification if, in addition to interpreting the style sheet as defined by the appropriate specifications, it supports all the features defined by this specification by parsing them correctly and rendering the document accordingly. However, the inability of a UA to correctly render a document due to limitations of the device does not make the UA non-conformant. L662: ### Partial implementations
L663: So that authors can exploit the forward-compatible parsing rules to assign fallback values, CSS renderers must treat as invalid (and 【873†ignore as appropriate†www.w3.org】) any at-rules, properties, property values, keywords, and other syntactic constructs for which they have no usable level of support.
L664: In particular, user agents must not selectively ignore unsupported component values and honor supported values in a single multi-value property declaration: if any value is considered invalid (as unsupported values must be), CSS requires that the entire declaration be ignored.
