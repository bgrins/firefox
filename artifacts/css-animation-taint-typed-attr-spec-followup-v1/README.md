# Typed attr: direct context versus alias provenance

The direct ordinary-property route has stronger textual support than the alias metadata route. Prior sealed audit/probe remain unchanged. No native, browser, or first-getter execution is claimed.

Scenario: an unregistered `--v` is actively supplied by a CSS keyframe with constant `horizontal-tb`; `writing-mode` is the ordinary sink. Its three keywords are valid, and the property is inherited and non-animatable. [Writing Modes 3](https://www.w3.org/TR/css-writing-modes-3/#propdef-writing-mode).

The direct call chain during style computation is:

1. Values 5 Appendix A, “Resolving in Properties”, property replacement step 1 starts substitution with the property name. General substitution step 1 guards that context for the call; step 2.4 invokes the function-specific replacement.
2. Typed attr replacement step 6 adds an attribute context and recursively substitutes the attribute text before typed parsing. The context discussion says guards “stack up”; it does not replace the outer property context. Raw-string/number/unit branches do not take this route. [Values 5](https://drafts.csswg.org/css-values-5/#attr-substitution).
3. Variables replacement step 3 makes an animation-tainted reference invalid in a non-animatable property; step 4 selects the nested var fallback. The active CSS keyframe satisfies the stated producer condition. [Variables 1](https://drafts.csswg.org/css-variables-1/#replace-a-var-function).
4. Typed parsing and property parsing accept the resulting writing-mode keyword. No metadata must survive into an intermediary custom property in this case.

Direct interpretation: the var in the attribute text is being substituted for writing-mode, despite the additional attribute cycle guard. The ordered text supports this binding; no new property evaluation is introduced by attr. **REACHED for the direct substitution decision**, scoped to this property-context interpretation, not a complete getComputedStyle invocation/scheduling proof. The spec does not provide a separate formal algorithm mapping the context stack to the phrase “being used in a property”. If implementers dispute that binding, that exact mapping is the clarification to request—not an invented rule that all attr-derived values are animation-tainted.

A small discriminator would use `data-v="var(--v, vertical-lr)"` and `writing-mode: attr(data-v type(<custom-ident>), vertical-rl)`. The nested var fallback prediction is vertical-lr. Horizontal-tb indicates admission of the animated value; vertical-rl indicates the outer attr fallback or inheritance, not successful nested fallback. Set the parent to vertical-rl. Add an untainted variable control and a literal attribute containing vertical-lr; capture source variable/timing/identities after the first sink sample. A missing-attribute arm with `attr(data-missing type(<custom-ident>), var(--v, vertical-lr))` is an optional simpler check: attr FAILURE step 7.3 directly enters the CSS-authored fallback. It does not exercise the attribute-text cache loss.

For the sealed alias probe, `--a: attr(data-v type(<custom-ident>)); writing-mode: var(--a, vertical-lr)`, the inner var is resolved while computing --a, which is animatable. Rejecting it there would choose the wrong context. The outer var guard only helps if --a acquires animation taint. Variables calls taint infectious for custom properties referencing tainted properties, but does not explicitly define whether a var reference discovered only inside fetched attribute text establishes that relation, or specify metadata preservation across this typed conversion. **INCONCLUSIVE for that alias bridge**. This remains a useful separately labeled provenance hypothesis; the direct trace does not silently settle it. [Variables taint definition](https://drafts.csswg.org/css-variables-1/#animation-tainted).

Attr-security taint is separate: Values explicitly propagates attr-derived taint through substitution and restricts URL use. That rule cannot be copied into an animation-taint requirement by analogy. Neither writing-mode case establishes a security issue. [Values attr security](https://drafts.csswg.org/css-values-5/#attr-security).

Suggested next execution: retain the sealed three-case alias probe as hypothesis-labeled; add the direct nested-fallback discriminator and its ordinary/literal controls in a separate fixture. Run original and installed engines before using it as an acceptance gate, then compare the candidate. Preserve both first and bounded later readings. No new fixture/runner or model is created here; runtime support and observed outcomes remain unknown.
