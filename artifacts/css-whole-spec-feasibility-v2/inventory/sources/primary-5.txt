L270: ### 2.3. Resolving Dependency Cycles
L271: 
L272: cite73†Custom properties are left almost entirely unevaluated, except that they allow and evaluate the cite74†var() function in their value. This can create cyclic dependencies where a custom property uses a var() referring to itself, or two or more custom properties each attempt to refer to each other.
L273: For each element, create a directed dependency graph, containing nodes for each cite73†custom property . If the value of a custom property `prop` contains a cite74†var() function referring to the property `var` (including in the fallback argument of var()), add an edge between `prop` and the `var`. Edges are possible from a custom property to itself.
L274: 
L275: If there is a cycle in the dependency graph, all the cite73†custom properties in the cycle are cite283†invalid at computed-value time .

Introduction
L83: 
L84: This section is not normative.
L85: 
L86: Large documents or applications (and even small ones) can contain quite a bit of CSS. Many of the values in the CSS file will be duplicate data; for example, a site may establish a color scheme and reuse three or four colors throughout the site. Altering this data can be difficult and error-prone, since it’s scattered throughout the CSS file (and possibly across multiple files), and may not be amenable to Find-and-Replace.
L87: This module introduces a family of custom author-defined properties known collectively as cite73†custom properties , which allow an author to assign arbitrary values to a property with an author-chosen name, and the cite74†var() function, which allow an author to then use those values in other properties elsewhere in the document.
L88: This makes it easier to read large files, as seemingly-arbitrary values now have informative names, and makes editing such files much easier and less error-prone, as one only has to change the value once, in the custom property, and the change will propagate to all uses of that variable automatically.
L89: ### 1.1. Value Definitions
L90: 
L91: This specification follows the cite75†CSS property definition conventions from cite76†[CSS2] using the cite77†value definition syntax from cite78†[CSS-VALUES-3] . Value types not defined in this specification are defined in CSS Values & Units [CSS-VALUES-3]. Combination with other CSS modules may expand the definitions of these value types.
L92: In addition to the property-specific values listed in their definitions, all properties defined in this specification also accept the cite79†CSS-wide keywords as their property value. For readability they have not been repeated explicitly.
L93: ## 2. Defining Custom Properties: the --* family of properties
L94: 
L95: This specification defines an open-ended set of properties called cite73†custom properties , which, among other things, are used to define the cite80†substitution value of cite74†var() functions.

L1898:

L144: 
L145: The value definition field of each CSS property can contain keywords, data types (which appear between < and >), and information on how they can be combined. Generic data types (cite127†<length> being the most widely used) that can be used by many properties are described in this specification, while more specific data types (e.g., <spacing-limit>) are described in the corresponding modules.

L150: ## 2. Value Definition Syntax
L151: 
L152: The value definition syntax described here is used to define the set of valid values for CSS properties (and the valid syntax of many other parts of CSS). A value so described can have one or more components.
L153: ### 2.1. Component Value Types
L154: 
L155: Component value types are designated in several ways:
L156: 
L157:   1. cite33†Keyword values (such as `auto`, cite132†disc , etc.) and at-keywords representing the start of an cite133†at-rule , which appear literally, without quotes (e.g. `auto` or `@media`).
L158: Note: It is possible, with cite134†escaping , to construct a cite135†CSS identifier whose value ends with `(` or starts with `@`. Such a token is an cite136†<ident-token> (i.e. a cite137†keyword ), not a cite138†<function-token> or an cite139†<at-keyword-token> .

L2283: ### Conformance classes
L2284: 
L2285: Conformance to this specification is defined for three conformance classes:
L2286: 
L2287: style sheet
L2288:     A cite950†CSS style sheet†www.w3.org .
L2289: renderer
L2290:     A cite951†UA†www.w3.org that interprets the semantics of a style sheet and renders documents that use them.
L2291: authoring tool
L2292:     A cite951†UA†www.w3.org that writes a style sheet.
L2293: A style sheet is conformant to this specification if all of its statements that use syntax defined in this module are valid according to the generic CSS grammar and the individual grammars of each feature defined in this module.
L2294: A renderer is conformant to this specification if, in addition to interpreting the style sheet as defined by the appropriate specifications, it supports all the features defined by this specification by parsing them correctly and rendering the document accordingly. However, the inability of a UA to correctly render a document due to limitations of the device does not make the UA non-conformant. (For example, a UA is not required to render color on a monochrome monitor.)
L2295: An authoring tool is conformant to this specification if it writes style sheets that are syntactically correct according to the generic CSS grammar and the individual grammars of each feature in this module, and meet all other conformance requirements of style sheets as described in this module.
L2296: ### Partial implementations
L2297: So that authors can exploit the forward-compatible parsing rules to assign fallback values, CSS renderers must treat as invalid (and cite952†ignore as appropriate†www.w3.org ) any at-rules, properties, property values, keywords, and other syntactic constructs for which they have no usable level of support.
L2298: In particular, user agents must not selectively ignore unsupported component values and honor supported values in a single multi-value property declaration: if any value is considered invalid (as unsupported values must be), CSS requires that the entire declaration be ignored.
