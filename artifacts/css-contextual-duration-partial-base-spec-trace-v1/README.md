This ambiguity matters **at initial setup too**. Prior Firefox and Chrome masked observations have composed font 32px but effect duration 1000ms after setup frames; their serialized CSS-duration values differ. Applying the ordinary composed-value argument consistently would predict 2000ms already at setup, not merely after the authored 24px mutation. The outline controls preserve measured initial timing; they do not prove that initial 1s is normatively correct. A rule that seeds timing from pre-effect style and updates only at particular later style changes needs an explicit update-boundary justification. The final 32px case makes pre-own and composed inputs converge and cannot choose between these explanations. No partial24 browser result is asserted here.

Three tempting shortcuts do not close the bridge. First, Web Animations' base value is the underlying value of the **target property being composited**. Its absence-of-animations step does not say to compute CSS animation control parameters in a base style. Second, [dependency-first property computation](https://drafts.csswg.org/web-animations-1/#computing-property-values), invoked by [computed-keyframe calculation](https://drafts.csswg.org/web-animations-1/#calculating-computed-keyframes), establishes animated dependencies for keyframe values; this is not itself a caller that selects CSS duration inputs. Third, [not animatable](https://drafts.csswg.org/web-animations-1/#animating-properties) excludes direct keyframe/transition processing. The accompanying recursion rationale is a note; it does not specify how an indirect em dependency in a control parameter is resolved. [CSS keyframe processing](https://drafts.csswg.org/css-animations-2/#keyframe-processing) likewise ignores non-animatable keyframe properties, rather than defining a pre-effect timing snapshot.

Values 4's parent-metric exception applies to font-affecting properties. This review has no explicit classification making the fade duration such a property, and its value cannot affect the independent constant-font effect. Do not import a feedback-cycle rule into this acyclic case. A genuinely self-dependent duration needs a separate cycle policy; descendant inheritance and parent publication need separate analysis too. Generic pending-style API requirements say updates must be available, but do not independently select the timing-input context, so the earlier broad getter-route census was not repeated.

A focused specification question, suitable for an issue but not filed: **For a CSS animation whose duration uses em and whose owning element has another animation affecting font-size, which computed-value context is used to generate and update iteration duration? Does it include the owning element's animation/transition effects, and if not, where is that exception and the recomputation boundary defined? Must the same rule apply at initial generation and after an authored-font change masked by an unchanged animated font? How should getComputedStyle(animation-duration), effect timing, and the rendered result correspond in the absence of API overrides?** The constant-font/opacity example avoids requiring a general cycle-resolution algorithm.
