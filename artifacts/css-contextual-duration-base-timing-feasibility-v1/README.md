# Pre-own-effect CSS timing: feasibility, not a policy decision

Gecko has a plausible full-style recascade primitive: `ServoStyleSet::GetBaseContextForElement` calls `Servo_StyleSet_GetBaseComputedValuesForElement`. It is not yet a proven drop-in source of CSS animation timing. The inspected implementation removes the target's animation cascade rules, then resolves the remaining rules using its inheritance parent's current primary computed style. It does not recursively remove ancestor effects. Thus it can represent an unanimated target inheriting already composed parent metrics, provided those parent metrics are current.

The C++ forwarding body is present in the previously authenticated branch capture (`same-query-repair-plan-v1/base`). The new Rust/resolver/value/cache bodies in SOURCE-EXCERPTS are public Searchfox captures, not an exact active-branch or built-binary join. No active source, runtime, app, Git or canonical state was read. No patch or execution is proposed here.

## What the existing APIs actually provide

`GetBaseComputedValuesForElement` returns the supplied style unchanged if it has no rules or removing animation rules does not change its rule node. Otherwise it creates a fresh thread-local style context and recascades the retained rule path. `with_default_parent_styles` reads `inheritance_parent().styles.primary()`, with separate layout-parent handling for display:contents. This is a current-parent input, not a saved pre-animation ancestor tree, and the helper does not flush or settle that parent.

`remove_animation_rules` removes every cascade level classified as animation: SMILOverride, Animations and Transitions. It is not a per-effect filter and cannot preserve another same-element font animation while removing only the opacity animation's contribution. Adopting this input would deliberately change the same-element DAG's timing interpretation as well as break some self-feedback paths. Whether transitions and SMIL should remain inputs is a separate policy question. The visited-style omission in the existing helper also needs to remain explicit.

`KeyframeEffect::mBaseValues` is unsuitable as a timing source. `EnsureBaseStyles` clears and rebuilds a property-keyed map only for animated properties needing additive values or certain scroll-timeline delay handling. It lazily obtains a full base context, extracts individual animation values and discards the full context afterward. It is neither an always-valid timing style nor a cache of every animation longhand. Underlying values for keyframe composition and CSS timing inputs are different data.

## Integration seam and preservation obligations

The retained `Gecko_UpdateAnimations` chain receives the current primary computed style from the Rust element wrapper. It passes that same style to CSS animation management, transitions and EffectProperties. The manager builds `ServoCSSAnimationBuilder` from it, reads `StyleUIReset()` timing lists, and resolves keyframes using the builder's style. Existing per-field script overrides are retained when updating an existing effect.

A prototype must separate the timing-list input from the composed style used by keyframes and EffectProperties. Replacing the shared `aComputedData` wholesale would also change keyframe em/lh resolution, display:none admission, transition before/after inputs and timeline handling. Even replacing the whole manager input changes its builder. A narrow explicit timing input alongside the existing style is a more reviewable shape, after deciding which animation longhands it covers; no API signature change has been implemented.

Task admission must use the chosen timing-input semantics. Comparing old/new composed `ui.animations_equals` is not proof that old/new base timing inputs are equal. A base value can change behind a masking own effect, or a composed change can leave base timing unchanged. The earlier animation-only guard cannot simply be assumed sufficient after this policy change. Recomputing only when an effect currently exists also misses inactive-but-specified CSS animations and first construction. Preserve API-owned duration/other fields, cancellation semantics, pseudo targeting and normal traversal behavior.

## Root units, caching and non-length inputs

The captured length implementation distinguishes target/root and descendant cases. On a non-root target, rem and rlh consult device root-font/root-line-height caches, independently of the immediate parent-style pointer. On the root, those units use root builder/reference-font or line-height special cases. Removing the root's own rules therefore is not equivalent to replacing shared root caches for descendants.

In the inspected flow, device root style/font size/line-height publication occurs after `data.set_styles` in matching's normal style publication; the base helper only returns a newly cascaded value. There is no call to that publication path in its inspected chain. Reads can nevertheless mark root-unit usage and lazily update root font metrics. This is not a claim of a side-effect-free helper. Temporarily swapping global device caches to base-root values would risk contaminating descendant resolution and invalidation, especially around parallel traversal. Do not do so without a separate scoped input design and exact branch audit.

The fresh helper context avoids relying on a persistent target base-style cache, but costs an extra recascade. Normal rule-cache reuse already tests effective zoom and font/line-height dependencies; this does not establish correctness of a new cached timing style. Such a cache would need dependencies on parent composed font/line-height/writing mode, root metrics and their generations, custom-property values and registrations, rule paths, pseudo identity and relevant viewport/container/font inputs. Equal rule-node pointers alone are insufficient. The unchanged-rule early return is safe only if the supplied style is itself current for those inputs.

Custom properties cannot be reduced to an em-only problem. Removing own effect declarations recomputes local variables but still inherits parent computed variables; registrations, fallback chains and non-inherited values can change the result. CSS Variables 2 explicitly describes infectious animation taint and invalid substitution into non-animatable properties, with fallback handling. That is distinct from excluding animation cascade rules. The inspected public source search found attr-taint machinery but did not establish an animation-taint implementation path; this is an unresolved applicability obligation, not a new bug finding or proof of absence. The held local custom-properties implementation was not read. See [Variables 2 definition](https://drafts.csswg.org/css-variables-2/#animation-tainted) and [variable replacement](https://drafts.csswg.org/css-variables-2/#replace-a-var-function). The current Variables 1 page and Variables 2 page differ here, so no cross-version equivalence is assumed.

## Decision boundary

This API supports investigation of pre-own-effect timing with inherited composed inputs; it does not establish that this is the required web behavior. It would not by itself complete late descendant work in a computed-style query. It also would not prove that rem caches, parent inputs or keyframe dependent properties have reached the needed generation. Existing first-read traces, the finite-depth experiment and the same-element interop uncertainty remain separate evidence.

Before a native prototype: authenticate the Rust/helper/value bodies against the intended branch; choose CSS-only versus all-own-effect exclusion and timing-longhand scope; define the shared-root and variable policy; preserve composed keyframe/EffectProperties inputs; and specify timing-input invalidation. Test own versus inherited em/lh, root rem/rlh, own transitions/SMIL, multiple effects, script overrides and variable fallback/registration cases under that explicit policy. No new fixture, owner, accepted fix or convergence claim is part of this artifact.
