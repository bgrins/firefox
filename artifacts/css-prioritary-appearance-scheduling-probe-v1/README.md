# Appearance/generated-scheduling discriminator

This isolated Mozilla WPT-style probe has five callbacks, one page and six callback/ending signatures. It is additional diagnostic coverage, not a replacement or expansion of the required 28-case publication comparator. Neither original nor candidate has run this fixture. The existing audit remains immutable.

The source-supported risk is graph Appearance → typed attribute → registered em length → FontSize, followed by generated ordinary FontSize → XTextScale → FontFamily → Appearance scheduling. The graph's active Appearance has not yet been marked ensured. Ordinary ensure can therefore substitute its declaration while the attribute cache still holds raw `var(--a)` or `var(--b)` tokens. A typed-length parse of those unresolved tokens fails, selecting the `base` fallback and potentially publishing APPEARANCE_BASE. After the descendant length completes, graph substitution can supply a valid length to Appearance; that is invalid Appearance grammar and computes to initial `none`. The flag is only inserted, not cleared. This source sequence is a prediction to discriminate, not an observed regression or a proved jointly reachable execution.

Registered `--a` and `--b` have distinct roles: one is a non-inheriting length with initial 0px and declared 1em; the other is a color with initial lime and declared light-dark(red,blue). The two target cases exchange the registration/value roles while retaining fixed registration and declaration name order. `SeenSubstitutionFunctions.var` is a PrecomputedHashMap, not declaration-order iteration. Mirroring reduces dependence on which name is visited first, but this fixture does not instrument or assert native traversal order. The color requests ColorScheme before its first getter returns. A UA Appearance-base rule supplies dark scheme, a 7px outline and monospace family. The ordinary UA rule supplies light scheme, zero outline and serif family.

Appearance is `attr(data-length type(<length>), base)`. The target attribute contains a var reference to the registered length. When that typed substitution succeeds, the resulting length is invalid for Appearance, whose initial value is none. The outer attr fallback is not selected merely because the consuming property rejects a successfully parsed length. Expected final observations are none/zero-outline/serif/light/red with registered length and literal font 20px then 30px. These endpoint assertions are research expectations awaiting both source roles; do not substitute the source prediction for observations.

Three controls distinguish setup from scheduling: literal-length supplies 20px/30px directly in the attribute and expects none with no gated rule; literal-none bypasses attr on Appearance and expects the same result; missing-attribute must select the valid base fallback, enabling the 7px/monospace/dark/blue rule. Button targets preserve the admitted UA base-appearance setup. Registration initials, grammar support, literal reference color and width, resolved custom length and font size are separately checked. Color reference values are ordinary light-dark under literal light/dark scheme. All properties are supplied in an ordinary non-forced Mozilla lane with appearance-base enabled.

Every phase records the first target custom-color getter and three passive frame-separated samples before querying target Appearance, scheme, family, outline, font and resolved length. Both phases finish before assertions. Thus an early Appearance assertion failure still includes the later marker/scheme/font values in its JSON diagnostic. The original could fail Appearance itself while the candidate resolves none but leaks eligibility; no outcome is required for either source in the diagnostic lane. PASS confirms all asserted endpoints but does not independently transport the hidden/window record. Root requested standard failure messages, so there is no modified testharness state, server receiver or custom PASS transport.

The ordinary UA sheet is removed before its iframe during test cleanup. Fresh iframe registration isolates cases. The page uses SpecialPowers and must run under `/_mozilla/` with the supplied pref metadata and shared `/resources/` harness. No expected-FAIL metadata is added. The first callback can fail before complete records if setup fails; that remains a setup failure, not evidence for the scheduling hypothesis.

Static preparation reuses the earlier Appearance probe checker: a genuine explicit-path Mozilla manifest, five inert callback names, and upstream path/content lint. Only the two expected SpecialPowers portability notices occur. This is not portable WPT conformance or a browser run. The Firefox frontend and mozlint skills were applied; no mach build, Git, native, app or index operation ran. `prepare.py` writes this owned directory and must not be rerun after sealing.
