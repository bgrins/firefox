# Min/max signed-zero tie audit

No credible tie-ordering defect was found in the inspected implementation. The ordinary `partial_cmp` operations are preceded by a sign-bit comparison, and the runtime helpers also handle differing signs explicitly. No probe, model, native patch, browser run, or acceptance claim is produced.

[CSS Values 4, infinities, NaN and signed zero](https://drafts.csswg.org/css-values-4/#calc-ieee) requires negative zero to compare below positive zero. Negative zero must be generated arithmetically; literal `-0` denotes positive zero. Nested calculations retain the sign until a top-level calculation censors it. These rules make a reciprocal observer meaningful, whereas directly reading a computed zero does not distinguish signs.

In the locally changed `servo/components/style/values/specified/calc.rs`, `Leaf::compare` first rejects different kinds and context-dependent percentage comparisons, then compares `is_negative()` results before reaching `partial_cmp`. The captured generic `CalcNodeLeaf::is_negative` uses `f32::is_sign_negative`, which distinguishes negative zero. Consequently opposite-sign zero ties cannot fall through to ordinary equality for numeric leaves exposing a coefficient. Generic min/max simplification selects by this ordering; incomparable inputs remain unresolved. The runtime `calc_min` and `calc_max` helpers independently choose the negative and positive operand, respectively, when signs differ. The captured generic resolver calls these helpers. This is source evidence, not an instrumented proof of all nested or contextual conversion paths.

Searchfox also identifies `testing/web-platform/tests/css/css-values/signed-zero.html`. Its helper observes sign through `clamp(-1, 1 / sign(expression), 1)`, and it includes both min/max operand orders and clamp combinations. However, its min/max inputs use literal `-0` and the min tests expect a negative result. Those particular expectations do not establish coverage of generated negative zero under the current specification. The older general `minmax-number-computed.html` capture lacks reciprocal-zero observers. This is a test-oracle caveat, not evidence that the native ordering is wrong, nor a claim about the current upstream WPT repository beyond the Searchfox-indexed file.

The audit does not exhaustively certify zero preservation during every leaf conversion, relative-unit resolution, nested operation, or percentage basis change. It dismisses the concrete hypothesis that min/max ties are decided solely by ordinary floating-point comparison. No new implementation bug or formal result is assigned. Any future coverage repair should generate negative zero arithmetically and distinguish NaN from either infinity, without treating this unexecuted audit as browser evidence.
