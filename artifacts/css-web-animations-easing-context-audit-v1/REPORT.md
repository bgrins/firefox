## Normative trace

1. Web Animations1, EffectTiming/update timing, checks whether the easing member parses as `<easing-function>`, then assigns it as the effect easing. The keyframe-processing algorithm uses the same easing syntax/error handling, including surplus unused easing strings. It does not invoke the target-property computation algorithm for these easing members. [Updating timing](https://drafts.csswg.org/web-animations-1/#updating-the-timing-properties-of-an-animation-effect), [keyframe processing](https://drafts.csswg.org/web-animations-1/#processing-a-keyframes-argument).
2. KeyframeEffect allows a null target; target is also mutable. Element.animate chooses a relevant Realm and document timeline, but those rules do not themselves choose a CSS computed style for easing arguments. Target-property values have a distinct context-dependent computation algorithm. That cannot silently be applied to effect/keyframe easing metadata. [KeyframeEffect](https://drafts.csswg.org/web-animations-1/#the-keyframeeffect-interface), [property computation](https://drafts.csswg.org/web-animations-1/#computing-property-values).
3. Easing defines a pure progress function and its numeric parameter grammar. It does not define a default element, default computed style or a prohibition on relative-unit subexpressions in those numeric parameters. Purity means a computed function has fixed parameters; it does not decide when context-dependent parameter expressions are evaluated. [Easing functions](https://drafts.csswg.org/css-easing-2/#easing-functions).
4. CSS Syntax grammar parsing produces a parsed structure; it is not a computed-value/style-context constructor. It leaves contextual validity checking to the calling specifications. [Grammar parsing](https://drafts.csswg.org/css-syntax-3/#parse-grammar).
5. Values4 gives initial font metrics for font-relative units used outside an element context. This is positive evidence for an initial-font interpretation **if** WA easing is defined as outside-element evaluation. It is not a general complete Context: viewport, root-font, container, sibling and environment inputs have separate rules. The inspected WA chain does not explicitly select the outside-element mode or when to resolve every dependency. [Font-relative units](https://drafts.csswg.org/css-values-4/#font-relative-lengths).

Thus REACHED for grammar-based easing parsing and separate CSS-property computation; INCONCLUSIVE for a fully specified contextual WA easing evaluation policy. There is no defensible deduction that type-correct `steps(calc(1 + 2 * sign(1em)), start)` must be rejected merely because the current native helper lacks Context. Conversely, there is no mandate to synthesize an arbitrary target/root style or hardcode16px. Do not turn this bounded negative search into a claim that no other CSSWG discussion exists.

A related open primary issue, [CSSWG13853](https://github.com/w3c/csswg-drafts/issues/13853), asks when/how WA rangeStart/rangeEnd relative lengths resolve. Its topic is range offsets, not easing; it corroborates that API grammar reuse does not automatically settle computation timing, but cannot supply easing's normative answer.

Inspected editions: WA1 8October2026, Easing2 23February2026, Values4 24August2026, Syntax3 20October2026. These are editor drafts. No issue was filed or external message sent.

## Exact native/API boundary

`TimingParams::FromEffectTiming` and update processing call `TimingParams::ParseEasing`. KeyframeUtils calls the same function for sequence and property-indexed keyframes. It delegates to ServoCSSParser and `Servo_ParseEasing`, which receives only string plus computed-output pointer. `parse_for!` supplies an author/no-quirks ParserContext and dummy URL data. That is syntactic configuration, **not** a default computed style or device context. The resulting specified timing function is immediately converted using `to_computed_value_without_context`.

KeyframeEffect construction has a document and optional target but parses TimingParams before constructing the effect. KeyframeUtils separately passes a document for property declarations; easing does not receive it. No target-style lookup or inherited font is in this chain. It is incorrect to describe the current helper as already using an initial/default style.

`Device::default_computed_values` is a real existing API, but requires a Device. The Device also has root style/font state; choosing its default values alone does not erase those other context dependencies. A default-style implementation would need an explicitly selected device/document, initial-vs-root metric rules, ElementContext, container fallback, timing and invalidation contract. Merely adding a document pointer or reusing the media-query context would not prove those choices correct.

CSS keyframe declarations are separate: `Servo_StyleSet_GetKeyframesForName` has element/style/document and can use the existing real animation-context path described in the predecessor. The CSS-property repair can therefore progress independently of inventing a WA context, provided every newly reachable context-free conversion is checked and the API admission limitation stays visible.

## Concrete prerequisite design

- Give the context-free conversion an Option/Result outcome. Resolve Steps with the existing context-free Integer resolver and function-specific clamp; propagate None through Servo_ParseEasing without writing output. C++ already turns false into TypeError. Preserve atomic update/error ordering and validation of unused easing strings. Do not use an arbitrary count fallback.
- CSS property ToComputedValue and CSS-keyframe conversion use their real Context and resolve Steps there; keep computed enum/FFI representation unchanged. Preserve installed118 rounding and the separate min2 jump-none contract.
- Treat API rejection of still-unresolved trees as a documented implementation limitation/safety gate, **not normative completion or proof of non-regression**.120 can change formerly folded API inputs into this failure path; include that transition in the hold assessment.
- For a future complete WA solution, first decide/obtain a specified context policy. An outside-element proposal can use initial font metrics for em-family parameters and resolve eagerly into fixed easing parameters, independently of target font mutations. But it must explicitly settle rem/viewport/container/sibling/env dependencies, realm/document selection, null/detached target, cross-document construction and re-targeting. It is a proposal, not an inferred mandate. A target-style proposal instead requires retained expressions/recomputation and different getTiming/getKeyframes semantics; it cannot be hidden inside today's string-to-computed helper.
- Do not retain the incorrect generic raw-coefficient Sign fold to make these callers continue accepting expressions.119 alone changes neither this folding nor the API signature, so the prior conclusion that119 can be validated independently remains unchanged.

## Existing tests and minimum missing tests

Its consumers include KeyframeEffect constructor, updateTiming, transformed progress and transformed distance tests. HEAD90's `animation-range-invalid.html` rejects relative range-offset inputs, including sign(100em−1px), but it tests a different member and cannot justify rejecting easing. The later public issue about range resolution further limits that analogy.

A policy-discriminating follow-up should record, separately, constructor options, updateTiming, sequence easing, property-indexed easing and unused easing; use null target and targets with16px/0px fonts, then mutate/retarget. Inputs: constant `steps(3,start)`, absolute `steps(calc(1 + 2 * sign(1px)), start)`, relative em counterpart, mixed em/px threshold (to distinguish actual initial font from a raw coefficient), and an explicitly unresolved sibling/container expression. Capture admission, exception, serialization and sampled output without assigning an invented expected default-context result. Existing invalid-string error-order controls remain normative.
