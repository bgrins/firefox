# Literal-zero prior art and oracle boundary

The [current CSS Values 4 signed-zero section](https://drafts.csswg.org/css-values-4/#calc-ieee) treats literal zero spellings as positive zero. This six-case observation follows that written rule, but it does not establish a new implementation defect or a compatibility-safe fix.

[CSSWG issue 7472](https://github.com/w3c/csswg-drafts/issues/7472) directly covers negative-zero tokenization and its reciprocal consequences. The fetched issue is open and labeled Needs Edits. [Tab Atkins's primary July 2022 comment](https://lists.w3.org/Archives/Public/public-css-archive/2022Jul/0195.html) explains that the Syntax algorithm produces mathematical zero, and distinguishes CSS from JavaScript's negative-zero parsing. The same comment also explicitly welcomes changing Syntax to match implementations if they preserve the negative sign. That compatibility qualification matters: a measured disagreement with the current prose should be reported as an existing spec/implementation boundary until this history is resolved, not automatically treated as a new release bug.

[Bug 1867380](https://bugzilla.mozilla.org/show_bug.cgi?id=1867380) is the resolved WPT synchronization task for [PR 43430](https://github.com/web-platform-tests/wpt/pull/43430), which introduced signed-zero tests. Its linked [bug 1867925](https://bugzilla.mozilla.org/show_bug.cgi?id=1867925) and [bug 1868231](https://bugzilla.mozilla.org/show_bug.cgi?id=1868231) were fetched through the Mozilla connector after direct web fetch failures. They are bulk WPT update tasks, not native literal-zero implementation bugs; the former was resolved fixed and the latter invalid. The indexed test nevertheless expects literal -0 to behave as negative within math. No per-file expected-FAIL metadata was found in the inspected branch/indexed sources.

Narrow primary-source searches did not identify a distinct native Gecko defect for literal-zero normalization. This is a limited search, not proof of absence. Existing min/max tie ordering is sign-aware, and no accepted math fix was identified as this literal-parsing behavior.
