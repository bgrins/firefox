# Finite scaled flex shrink weights overflow before accumulation

Locally validated native repair; independent source review is pending. This is one new browser-confirmed layout bug, with no security claim and no new committed-fix count. Suggested triage P3: ordinary-size items are visibly wrong, but reproduction requires unusually large finite shrink factors.

Two100px items in a150px container with shrink factors1e38 and2e38 should become about83.333px and66.667px. The original implementation yields75px each. Factors3e34 and6e34 instead yield100px and50px because only the latter scaled weight overflows. Equal factors on unequal bases also distribute shrink incorrectly. CSS Flexbox's resolving-flexible-lengths algorithm requires ratios of shrink factor times inner base size: https://drafts.csswg.org/css-flexbox-1/#resolve-flexible-lengths . The factors are finite and their computed CSS values were retained by the browser.

Discovery came from source analysis during the floating/provider verification work, followed by browser reproduction. GetWeight returned float and multiplied mFlexShrink by mFlexBaseSize in float; assignment to the double accumulator happened too late. Overflow selected the equal-largest-weight fallback and destroyed finite ratios. The fix returns double and explicitly promotes mFlexShrink before multiplication. Existing zero-base handling and true-infinite handling remain intact. Both call sites were checked through Searchfox.
