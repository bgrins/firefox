# Subgrid expanded-name cache: bounded arithmetic proposal

Status: source proposal only; not compiled, browser-tested, installed, or accepted. Three native paths, no WPT. Originals are exact HEAD90 objects; no live native/index/build/browser changes. This replaces the earlier strategy note's conditional INT32_MAX producer-cap preference with usize::MAX saturation and a guarded full-width consumer. It does not change the independently recorded Integer::resolve stored-range defect.

## Exact change and invariant

The Rust repeat product and parser prefix sum use saturating_mul and saturating_add. The cache remains usize, with its field comment documenting saturation. C++ first clamps its signed line cap to zero, promotes it to size_t, compares the complete cache, and subtracts only when the cache is smaller. The resulting difference is at most INT32_MAX before conversion to uint32_t. The patch does not narrow the cache to signed32, perform signed subtraction with it, or change append loops, repeat remainder handling, or grid placement.

For admitted nonnegative repeat counts and list lengths, the cache equals min(usize::MAX, E), where E is the exact expanded fixed-name count. On Gecko's 32/64-bit size_t targets, every positive int32 cap C fits that storage bound. The guarded consumer therefore returns max(0,C−E); overflowed exact counts cannot create extra auto-fill room. Independently of that producer meaning, the consumer arithmetic is defined for every int32 cap and arbitrary size_t cache. A nonpositive cap returns zero remaining auto-fill capacity. That arithmetic guard is not a proof that a negative layout cap or its preceding placement was valid, nor that later append logic handles it correctly.

The positive-count semantic premise is material: historical Integer::resolve can omit a stored positive clamping mode. Zero/negative calc counts can consequently disagree with computed counts. The usize cast and new saturated operations remain defined, but this proposal does not claim their cached value is the mathematically intended positive repeat count. The separate Integer range proposal addresses that producer issue; this patch is independently useful for positive counts and does not require its code.

## Why the consumer guard is necessary

Normal line resolution uses explicit line bounds (kMinLine=-10000, kMaxLine=10000, translated bound 20000), ordered definite ranges, constrained automatic placement, and translation/reversal that preserve valid extents. Those paths support small nonnegative caps under their defined-state premises. They do not establish a universal nonnegative cap for every call.

A separate source lead exists for absolutely positioned subgrids: Grid::PlaceGridItems temporarily untranslates mGridColEnd/mGridRowEnd with AutoRestore, translates definite item endpoints, and calls SubgridPlaceGridItems before restoration. The latter substitutes parent end−1 for an automatic end. With a nondefault explicit-grid origin these representations can differ; an unsigned extent can then be unsuitable for the signed cap. No browser reachability or corrected placement is claimed here. The native guard deliberately does not depend on closing that separate source obligation.

Prior fix24 (commit 7f5a1105253e60b283174ea890862b1943e8702a) changes abspos numerical line-clamping in ResolveLineRange/ResolveAbsPosLineRange, not this temporary-origin/automatic-end mapping. Its test uses absolute children inside a subgrid rather than an absolutely positioned subgrid itself. Pending hidden-grid repair108 concerns dirtying skipped in-flow children. Neither comparison establishes a new bug; the origin lead remains separate and unaccepted. No abspos fixture or placement change is included here.

## Policy tradeoff and remaining validation

usize::MAX saturation preserves every exact representable cache and the existing field type. It avoids introducing a redundant INT32_MAX producer ceiling once the consumer compares at full width. The previous signed subtraction cannot be retained with this policy. A producer-only cap would also fail to discharge the separately discovered signed-cap premise. The selected two-sided change protects arithmetic while keeping placement policy outside its scope.

The generic count model and guarded-consumer companion support the stated mathematical contract; they do not prove Rust/C++ extraction, parser semantics, allocation/cardinality reachability, generated ABI, or complete layout. The companion's negative-cap result is only an arithmetic identity. SOURCE-PINS.json binds exact original/candidate bodies; proposal.patch contains only the described edits. TRANSPORT.json records real scratch Git check/apply/reverse-check/reverse and exact postimages, with scratch removal. No native/helper compile, formatter, WPT run, or browser result is claimed.
