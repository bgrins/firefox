# Independent terminal review plan

This is a plan for a small adaptation of the executed terminal reviewer, not execution authority or a claim of a clean-original result. Bind the final active owner seal and root's actual session/launch/terminal/exit arguments after the owner terminates. Authenticate the owner and its full source/resource/helper closure first. Do not reuse a guessed candidate result schema or hard-code an expected PASS count.

The clean-original producer uses `RESULT.json` with `phase`, `provider_source_role: clean-original`, `build_revision`, `success` and restoration fields. Its admission is `BUILD-PRE.json`; the build is `original-build`; the browser phase is `original-wpt`. The phase hashes join ASSESSMENT/raw/RESULT. This differs from the prior candidate's CANDIDATE-PRE/CANDIDATE-RESULT/candidate_phase names. Preserve owner exit and browser exit separately.

For a completed browser phase:

1. Replay the entire raw stream through the final owner assessor and exact ASSESSMENT-POLICY, including all125 callback identities, eighteen ordered page endings and setup-error detection on every page. Require exact replay equality and complete lifecycle, not a passing-count prediction. Recount PASS/FAIL and compare full rows/endings with OUTCOMES. Do not compare it against held-original as the admission oracle; any secondary held comparison must report differences separately.
2. Join actual build command/exit/group cleanup, COMMAND source hashes, successful build RESULT and all rebuilt binary hashes to original-wpt/BINARY-PINS. Join browser application metadata before/after and run_info to the actual new build/harness revision and original role. This newly compiled app must not inherit the historical20ab BuildID or binary hashes. New build identity is whatever the final admitted HEAD specifies.
3. Verify the clean provider8a4 build image and exact unchanged context bases, including the other three taint files, against the final owner source roles/context pins and build/phase snapshots. Verify the temporary native working-diff set is empty. The restoration preimage is owned held2675, not committed8a4. Authenticate the native-clean-provider candidate recipe separately; no candidate outcome is supplied here.
4. Check phase PRE/POST and PHASES-PRE/POST equality, resource/manifest/copied metadata hashes, original application metadata symmetry during WPT, and RESULT's preserved phase joins. Require expected absent metadata to remain absent. Verify owned build/wake/WPT groups and the exact temporary profile root are absent.

For restoration, reuse the executed full-state/application/extra-file/source identity checks. Compare BUILD-PRE to POST modulo only the observed raw-index field; then independently verify current restored state, semantic index, flags and canonical controls. Verify held provider bytes/inode and all unaffected native contexts, original application semantics/binaries/BuildID/provenance, extras and source-transition-lock absence. Current restored app inode identities may differ only with exact semantic restoration evidence. Join BACKUP-CLEANUP to BACKUPS and restoration; verify only the owned backup is absent on lifecycle success. If a failed build or incomplete phase retains backup, preserve that failure and use the separate verified cleanup path rather than treating missing browser output as success.

Only after review succeeds may root append actual terminal/review receipts and freeze regular-file hashes plus explicit borrowed-tools symlink inventory. A raw-index-only epoch refresh, if necessary, is a separate root-owned operation with exact before/after fields and rollback. It must not relabel clean-original results or rewrite an old held baseline. The clean candidate can then bind the frozen clean-original raw result, independently compiled sources/binaries/metadata, and the post-restoration current admission. No identical-binary or identical-app-inode assertion is valid across the two builds.
