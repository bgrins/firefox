# Computed names in the existing guarded variable profile

This standalone extension evaluates a substituted property-name argument before resolving its target. It reuses the canonical guarded-state operations, old expression evaluator, completion/base policy, and finite remaining-binding discipline. It does not replace the canonical library. The unused-static-fallback witness was already covered; it is not counted again.

`Names.lean` adds `Expr.reference` and `Expr.fallback` whose first argument is an expression. `Expr.static` embeds the complete old `VariableExpr`, including its own append/reference/fallback forms. Name evaluation returns both tokens and state; name decoding retains that state, successful decoding resolves the target in that state, and only an invalid primary evaluates fallback. Ordinary append still evaluates the second expression after a failed first expression.

The solver's recursive guard/completion/pop shell is the existing `GuardedCompletion.resolve` pattern instantiated with this enlarged expression type. It calls the canonical `GuardedState.markCycle` and `pop`, not a new cycle algorithm. Termination decreases the finite remaining declaration list on every bound-property expansion; there is no arbitrary fuel or name-length bound. Dynamically selected missing names use the supplied base environment; repeated active names are detected before the remaining-list lookup.

## Proven bridge and state obligations

* `embedded_resolve` equates the entire `(value, marks)` result to canonical `GuardedCompletion.resolve` for every embedded finite binding list, arbitrary active/marked stacks, requested name, parser, base and completion callbacks. It is not just a fresh-root value equality. The proof uses the canonical removal/termination lemma and equality of recursive resolver callbacks, then the unchanged old expression evaluator.
* `evaluate_preserves` lifts any resolver state invariant through name evaluation, decoding, lookup and fallback. Its static case directly reuses `GuardedExpr.evaluate_preserves`.
* `resolve_marks` extends the canonical containment/preservation argument to the new expression forms. Existing caller marks cannot disappear; returned marks belong to the active stack when the incoming marks do. `fresh_marks` consequently gives an empty returned mark list for fresh queries; invalid owner values remain invalid even though their marks are popped.
* `name_state`, `invalid_name_state`, `fallback_only_after_lookup`, and `fallback_threads_state` expose the relevant sequencing equations. `embed_lookup`/`embed_remove` are the bridge's list lemmas.

The removal, mark-preservation and fresh-mark proof patterns are adapted from their pinned canonical counterparts. They are proof transfers/generalizations to the enlarged syntax, not independent coverage credit for the old guarded solver. This prototype has no separate new relational semantics or native refinement theorem.

## Explicit parser boundary

`NameAdapter` packages `parse`, a caller-supplied `accepts` relation, and the exact correspondence `parse tokens = some name ↔ accepts tokens name`. The generic evaluator/solver accepts the parser projection; its algebraic/state theorems hold for every parser. A CSS interpretation requires the caller to establish that `accepts` is the appropriate exact custom-property-name parsing relation. Merely instantiating the structure with an invented relation does not prove CSS parsing.

The examples use normalized tokens `Token.name name` and `Token.text text`. The adapter accepts exactly one already-classified name token, preserving its String identity; it rejects empty and multiple tokens and text tokens. The name tag is an explicit normalized-input premise. It does not recognize CSS escapes, whitespace, token concatenation, name validity, case conversion or raw `var()` syntax. No reserved/sentinel property name represents a failed parse. This boundary also excludes attr taint, spread, registered-property defaulting, animation providers, custom function/context identities and animated cycles. Completion/base functions remain explicit parameters; examples use ordinary unregistered identity completion and an empty base.

The `inner_mark_survives` result is `(some [20px], [--x])`: the inner fallback returns tokens, but its caller's mark survives and the enclosing `--x` resolution is invalid. Dropping that state would change the result.
