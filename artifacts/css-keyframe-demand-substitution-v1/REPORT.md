# Demand propagation through actual endpoint substitution

This four-path proposal adds a demand-aware route through the real substitution and retained-endpoint resolver. It does not enable pending animation production or change the real cascade iterator/admission. The preceding completion package remains separate. The new native code and presentation test are uncompiled and unrun.

`substitute_one_reference` checks the pending set at the actual `var()` evaluation point, before looking up a possibly stale typed/universal value or treating an omitted provider as missing. It returns `SubstitutionDemand::Provider(Name)`. Recursive substitution propagates that result without converting it to CSS-invalid or taking fallback. Only the existing CSS-invalid result takes the existing fallback/defaulting path. Fallback traversal is the existing execution path, not a lexical scan of all references.

The ordinary public substitution entry points always supply no pending set. Their existing apply/defaulting operations are reused. No ordinary SCC traversal, graph construction, cycle invalidation, prioritary-property application, or cascade winner gate is changed. Lazy evaluation requests do not settle normative cycle dependencies or the owner/lifetime of animated endpoint versus final-property guards. The historical graph formulation and current draft substitution-context formulation must be distinguished by the separate spec trace; this package makes no new cycle conformance claim.

`KeyframeEndpoint::resolve_registered_with_pending` owns its supplied context. It obtains the current registration and original retained declaration, then uses the actual substitution, registration parsing, computed-value conversion and invalid defaulting. It returns the real `AnimationValue` and its native metadata; no token mock or cached endpoint value is substituted. Existing CSS-wide, guaranteed-invalid and unsupported declaration handling is delegated unchanged. With an empty pending set it calls the existing resolver, whose body is byte-identical. With pending providers, it does not invoke the old attribute-builder traversal prematurely.

Typed `attr()` evaluation with any pending provider returns `AttributePreparation` before consulting the prepared attribute map. This includes typed attributes reached recursively through another provider or a selected fallback. An unused typed fallback is not evaluated. Raw-string and unit attributes still use the current target tracker. This is an explicit incomplete preparation result, not invalid CSS or a value; it conservatively stops some otherwise evaluable inputs. Typed-attribute/prioritary traversal must gain genuine demand propagation before widening production admission. When all providers are ready, the existing resolver prepares typed attributes normally.

The caller must construct a fresh context and fresh tracker for each attempt and retain the supplied provider map as a coherent snapshot. A tracker can observe attributes before a later demand occurs; those observations must be discarded or buffered, never published from incomplete work. Consuming the context prevents its partial values from escaping through this API, but the mutable tracker remains an explicit ownership obligation. The test bridge uses the same actual context construction as the existing resolver FFI, with fresh cache conditions, tree-counting state, target and current provider style. It reports attribute observation without publishing a style. Production must still preserve and merge successful cacheability/watch effects through the completion owner.

The new presentation test proposes ten real-resolver calls: pending over stale `20`; retry with completed `20`; unused fallback; used fallback demand; wrong-type primary producing the actual registered initial `10` rather than fallback; both invalid-first and pending-first orderings; typed-attribute incomplete preparation; completed typed attribute `40`; and a final clean `20` call after errors. It retains all existing presentation tests. These are source proposals, not passed tests. The FFI bridge accepts one pending name to keep the host test narrow; the actual native resolver takes an owned-name set and has no one-provider restriction.

The callback connection to the preceding scheduler is now concrete: build the pending-name set from `ProviderView::pending_names`, create an isolated native context from ready winners plus the current element/font/color state, call `resolve_registered_with_pending`, map `Provider(name)` to `Demand::Provider`, and retain `AttributePreparation`/unsupported work as incomplete errors. `Ready(None)` must remove the provider from that context while remaining distinct from a pending name. Only the scheduler's complete result can publish. A future actual collector must establish priority/revert/seen winners before this step; no test-only supplied winner table proves that admission.

This route can compute the existing registered-number leaf endpoints against a completed unregistered provider changing `20 → red → 20` using the existing real defaulting path. It has not repaired that browser history: there is still no pending source item entering the real collector, no completed winner map replacing cached normal rule output, and no defined animated-cycle completion policy. Endpoint scope, typed attributes, prioritary dependencies, successful side-effect merging, and current implicit-base semantics remain open. Costs include pending-set construction and retry work; no performance claim is made.

Validation is limited to formatted-source parsing and exact scratch forward/reverse transport, plus source checks that the old endpoint resolver/FFI and existing presentation tests remain intact. No native compilation, host execution, browser run, live source/index/canonical/ledger modification, or bug acceptance occurred.
