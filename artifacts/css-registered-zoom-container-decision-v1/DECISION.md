The current standards evidence supports that implementation choice. [Conditional 5 container units](https://drafts.csswg.org/css-conditional-5/#container-lengths) use size-query rules and select the eligible ancestor independently for each axis; its [width](https://drafts.csswg.org/css-conditional-5/#width) and [height](https://drafts.csswg.org/css-conditional-5/#height) features read the source content box. [CSSWG issue 10268](https://github.com/w3c/csswg-drafts/issues/10268#issuecomment-2192195262) resolved “use chrome/firefox behavior”: the accompanying discussion identifies the container's own CSS-pixel frame. The [editor's follow-up](https://github.com/w3c/csswg-drafts/issues/10268#issuecomment-2269576031) specifically proposes unscaled box bounds. That is strong standards intent for source-relative unscaling, although the issue remains open with Needs Edits and its linked WPT tests queries, not container units.

[Viewport](https://drafts.csswg.org/css-viewport/#unscaled) defines unscaled length relative to an element by dividing its scaled length by that element's effective zoom. Its used-value and [CSSOM](https://drafts.csswg.org/css-viewport/#zoom-om) rules separate scaling for layout from unscaled computed-style output. [Registered-value computation and substitution](https://drafts.css-houdini.org/css-properties-values-api-1/#calculation-of-computed-values) convert a typed dimension to its canonical unit before it is serialized into a consumer. Together with the resolved query-coordinate intent, the sensible pipeline is source content size / source effective zoom, canonical registered pixels, then the consumer's ordinary used-value zoom. It is not source content size / target zoom.

The narrow published-text trace remains **INCONCLUSIVE** at the size-query coordinate read: the current draft still lacks an explicit unscaled-bounds sentence. This record does not rewrite that earlier verdict. It distinguishes sufficient implementation/reviewer justification from a completed normative derivation. The missing editorial clarification should be noted in the review, not treated as evidence that the known ordinary container-unit behavior is correct.

The source change is coherent with that choice. `ContainerSizeQueryResult` retains each physical dimension with the effective zoom of the selected source; merging preserves that pair. `resolve_size` converts each axis before `cqmin`/`cqmax`. The small-viewport fallback is already a separate coordinate input and is not divided by a container or target zoom. The registered conversion scope and custom-property CSSOM paths then agree on canonical storage. Ordinary container conversion does not enter this scope, so this patch does not claim to repair bug 1894104. Observed preservation of ordinary controls is compatible with that deliberately bounded scope.

Removing only `container_rule.rs` is not a sound smaller fix. The specified-length caller now consumes f64 pixels, and retaining a source-scaled container leaf inside canonical `calc(10px + 100cqw)` mixes coordinate frames. Dividing that mixed result by target zoom also corrupts the absolute term. Restoring the old Au API and adding a target-unzoom special case would compile after adaptation, but would encode the wrong source frame whenever source and target zoom differ. A per-value exception requires provenance through expressions, lists, substitution, serialization and query operands; that is a larger alternate design, not a minimal narrowing. Keeping per-axis f64 conversion also avoids re-quantizing an unscaled dimension back to integral app units before multiplication or min/max.
