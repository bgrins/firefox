This isolated Lean model describes a proposed sender-side protocol that separates pending non-throttled work from a dispatch-attempt bit. It adds obligations missing from the earlier seven-theorem pending/posted model: preserve PreTraverse eligibility through deferral, retry an already-pending entry at a genuinely safe external boundary, and avoid duplicate dispatch attempts before consumption or explicit invalidation. It is not a native patch, a model of the existing candidate, or a refinement proof.

`canDispatch` requires all three flags to be false: inServo, inPreTraverse and inStyleRefresh. The source review establishes that post-traversal tasks can run outside Servo while the wider style-refresh scope remains active. Leaving traversal alone therefore does not establish this predicate. The current logger does not record style-refresh state; its outside-Servo/outside-PreTraverse events cannot authenticate the model's safe boundary. The later instrumented candidate observation reported by root motivates this distinction but is not an input to these proofs.

`request` marks non-throttled work pending. If dispatch is blocked, it leaves an unattempted entry retryable. If safe and unattempted, it emits exactly one abstract attempt and records that fact. If already attempted, it coalesces. `externalBoundary` explicitly clears all three context flags and performs no request, post, service or traversal; its use is a premise about a later caller, not a claim that every native traversal exit reaches that boundary.

Six audited declarations establish the useful contract:

- Any request retains pending eligibility and preserves the independent root-queue, timing-version and composition observations.
- Any positive finite batch of blocked requests with no prior attempt leaves exactly the same unattempted pending state.
- Leaving Servo/PreTraverse while style refresh remains true still defers.
- Any finite batch of requests for an already attempted pending entry coalesces without changing the attempt counter.
- After any positive blocked batch, one request at the explicit safe boundary emits exactly one attempt; any later requests without reset or consumption leave that exact state unchanged. This is the central new retry/coalescing result.
- Attempt invalidation preserves eligibility, whereas consumption clears eligibility and the attempt bit. Neither administrative event asserts composition or changes the independent receiver observations.

`rootQueued`, timingVersion and composedVersion are abstract environment observations. The sender's emission is separated from receiver handling, so an attempted call does not establish that a root was queued or composition occurred. Their preservation here is a frame property of that chosen sender step, not a claim that a real synchronous PresShell call cannot affect them. A request also need not change effective timing. The earlier model's successful `service` abstraction is deliberately absent; this successor proves a finite opportunity to attempt dispatch, not delivery, fairness or rendering progress.

The administrative transitions are obligations for an implementation. `consume` represents actual consumption, cancellation or table removal authorized elsewhere; this model does not prove when that operation is valid. `invalidateAttempt` represents explicit knowledge that an earlier attempt no longer covers pending work. There is no automatic retry, drain-on-exit, fixed-point loop, timer or global convergence theorem. Without a later safe request or an independent wake, pending work can remain indefinitely. If a dispatch attempt does not establish a usable wake and is never invalidated, the attempted state can likewise coalesce indefinitely.

This models the more explicit representation discussed in the sealed repair-options review, not its smaller “retry every safe external request” experiment. That smaller variant can repeat posting side effects; the captured `PostRestyleEvent` increments an undisplayed-restyle generation even when hints may later coalesce. The one-attempt property therefore matters. Native implementation still requires exact branch applicability, all direct posting callers, throttled-entry handling, PreTraverse eligibility/removal, pseudo-target or missing-context failure, and safe table-entry reacquisition after potentially mutating calls. Throttled requests and actual table allocation are outside this non-throttled protocol.
