The Inspector Rules view can show an applied CSS style rule with no declarations when a custom property starts with a balanced `{ ... }` value. It also hides otherwise valid declarations after the custom property. Because those declarations have no Rules editors, they cannot be edited there or tracked through the normal Inspector Changes workflow.

Minimal testcase:

<style>
div { --payload: { a: b; c: d }; color: red; margin: 0; }
</style>
<div id="test">sample</div>

Steps to reproduce:
1. Load the testcase in Firefox.
2. Inspect `#test` and look at the `div` rule in the Rules view.
3. Compare the displayed declarations with `document.styleSheets[0].cssRules[0].style` in the page console.

Actual: The `div` rule is shown with zero declarations. CSSOM retains `--payload` as `{ a: b; c: d }`, `color` as `red`, and `margin` as `0px`; the element's computed color is red. The three authored declarations are absent from Rules.

Expected: Rules shows the custom property and the following `color` and `margin` declarations, allowing the latter two to be edited normally.

This CSS is valid. CSS Custom Properties Level 1 permits balanced blocks and semicolons inside a custom property's value; the semicolons in this testcase are inside the `{ ... }` block. See https://www.w3.org/TR/css-variables-1/#syntax . The live Firefox CSSOM and computed style independently confirm that the declarations parsed and applied.

Reproduced in two fresh Firefox Nightly 159.0a1 profiles and one fresh Firefox 157.0 profile on Linux. The attached browser-chrome regression test passes six CSSOM/live-rule checks and fails only the assertion that Rules shows the three authored declarations. Attached are the standalone test patch and three-run evidence.

Likely cause: `parseDeclarationsInternal()` in `devtools/shared/css/parsing-utils.js` treats every top-level `CurlyBracketBlock` token as the start of a nested rule when `currentBlocks` is empty. It does not check that a custom property's value is already in progress (`lastProp.isCustomProperty`). It then discards that declaration and stops parsing before `color` and `margin`. This code remains in the latest Firefox main revision checked on 2026-10-04.

Duplicate check: Reviewed 2,112 public Inspector: Rules summaries and targeted public searches for custom properties, braces, blocks and declaration parsing. Bug 1544223 was fixed for a complex custom-property block nested inside parentheses, where semicolons produced bogus declarations; this minimal bare `{ ... }` value now causes the nested-rule detection to discard the custom property and all following declarations. Bugs 1841502 and 1946445 concern different shorthand fallback or actual nested-rule behavior.

This is a functional DevTools defect (S3). No security impact is claimed.
