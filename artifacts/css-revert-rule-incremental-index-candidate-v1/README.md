# Incremental owner index: separate C candidate

This is an unadopted source alternative to exact indexed cascade.rs preimage `b454e10310175f3c41bbe8cadde6fb8d0b12ee3e1bb900f91422cd44cad453f3`. Only the copied cascade.rs changes. The existing C stylist.rs source-view argument and coherent A+B+D applicable_declarations.rs remain prerequisites; SOURCE-ROLES.json pins all four roles. No production source/index, native build, browser or benchmark was changed or run.

## Mechanism and semantic boundary

The first admitted Rule still creates the same optional boxed exclusion state. Construction now retains a source cursor and empty tables. `DeclarationSourceIndex::owner` first probes cached original-entry addresses, then advances the retained Rules cursor only until the requested declaration's block has been indexed. The direct Block source is consumed once. Each visited distinct block contributes all its entries; a retained block-address set prevents duplicate block enumeration. The cursor advances across source-less nodes too. An original in a previously visited block is a cache hit. Nothing walks an untouched source suffix merely because the first Rule was encountered.

Before owner lookup, `RuleExclusions::contains` tests a separate set keyed by physical longhand and full `priority.unimportant()` equality. When that prefix has no exclusion, it returns false without indexing. This matters when a lower-layer winner is examined after a higher-layer Rule. A matching prefix still requires the exact original-entry owner; matching priority does not imply matching block. The flat final exclusion set preserves the full tuple (physical longhand, normalized full priority, block allocation). Derives retain flags/context/origin/layer equality, rather than ordering equivalence. Raw pointers remain equality/hash keys only, never dereferenced.

The prefix set equals the projection of the full exclusion set after each successful insertion. No prefix is inserted before owner resolution. Each successful source-index extension maintains an exact original-entry-to-live-owner map for all distinct blocks in the visited source prefix; the cursor denotes the next unvisited source node. Thus an owner hit is sound, and continued enumeration is complete for an applicable original under the existing producer contract. These are proposed proof obligations, not new Lean theorems or a Rust verification claim. They can extend the existing ownership/index membership bridge. A missing owner still panics when identity is needed; a missing exclusion prefix avoids asking for it.

No per-declaration field, declaration-buffer change, raw-pointer dereference or common-path allocation is introduced. Both constructors retain `rule_exclusions: None`. Existing seen/inclusion/cumulative-cutoff guards, substitution's original declaration pointer, physical-property mapping, custom properties and dispatchers are byte unchanged apart from the mutable exclusion lookup needed to advance the cursor. The retained borrowed source/guard view has the existing cascade lifetime; the new index is dropped with the boxed exclusion state.

## Choice and cost

For a visited source prefix of S_p nodes and D_p entries across B_p distinct blocks, R distinct full exclusions, G distinct property/priority prefixes and Q checks/insertions, expected hash-table work is O(S_p + D_p + Q), with auxiliary storage O(D_p + B_p + R + G). Worst-case queries can visit the entire source view. Enumeration is by complete blocks, so one huge requested block still costs all of its entries. The deduplication set now persists with the cursor, unlike the eager implementation's temporary set. Repeated checks add a prefix probe before the owner/full-key probes. These are source-derived bounds, not measured speed or allocation-size results.

The chosen representation is a flat full-key set plus one prefix set. Grouping prefix→block-set would save repeated key bytes for a one-property chain, but would allocate an inner set per physical property/priority prefix; `all: revert-rule` and many-longhand blocks could produce many such allocations. The flat design keeps two exclusion-table allocation families, at the cost of O(G) prefix storage and repeated prefix bytes in full keys. An inline-first-block group could reduce that cost, but adds another representation transition; it is not required for this bounded candidate.

A small-list→index threshold could reduce constants for tiny Rule counts. It retains repeated owner searches/exclusion scans below the threshold, introduces a workload-dependent threshold and can trigger a whole-source allocation cliff when promoted. Incremental indexing instead targets avoidable source suffix work directly, without a tuning constant. It is not automatically faster for tiny cascades, long chains or many distinct prefixes. In particular chain256 can still index most/all relevant blocks; the reported roughly 2x indexed slowdown is not declared solved by this patch.
