# Masked duration: current specification trace

**Question:** After changing the authored font from 16 px to 32 px under a constant 32 px font animation, must the existing contextual opacity animation use a 2000 ms duration and return .375 on the first computed-opacity read?

**Scenario:** A connected, rendered element has two existing CSS animations with unchanged names, targets and effects. Both are ready and paused at 750 ms. The font animation has constant 32 px endpoints and fixed timing. The opacity animation has explicit 0/1 endpoints, normal direction, linear easing, one iteration, zero delay and `calc(1em / 16px * 1s)` duration. No duration override, effect replacement, transitions, scroll timeline, important opacity rule or competing opacity effect applies. This is the sealed masked fixture, not the separate ownership controls.

## Normative obligations and algorithm boundary

1. [CSSOM `getComputedStyle`, step 5](https://drafts.csswg.org/cssom/#dom-window-getcomputedstyle) requires the returned declarations to contain the resolved value for the connected rendered target. Step 6 returns a live declaration object. For opacity, [resolved values](https://drafts.csswg.org/cssom/#resolved-values) use the computed value. This is the actual first-query entry point; it does not explicitly invoke the CSS Animations pending-style section.
2. [CSS Values 4, font-relative lengths](https://drafts.csswg.org/css-values-4/#font-relative-lengths) defines `em` from the element's computed font size. At the final state, both the authored base and animated font are 32 px, giving `(32px / 16px) * 1s = 2s`. This arithmetic does not choose between the disputed initial base-16 and composed-32 input policies.
3. [CSS Animations 2, animation duration](https://drafts.csswg.org/css-animations-2/#animation-duration) states that the property “specifies the iteration duration” of the associated effect. [Animation updates](https://drafts.csswg.org/css-animations-2/#animations) require CSS property changes to update the corresponding animation and associated objects, subject to API overrides. None of the duration/effect override exceptions applies here. The paused state is not a duration override.
4. [Pending style changes](https://drafts.csswg.org/css-animations-2/#requirements-on-pending-style-changes) requires consistent results from its own programming interface and Web Animations operations returning CSS-animation objects or state. That directly constrains a subsequent `getAnimations()` or effect-timing query. It is not an express rule for the earlier CSSOM getter. Moreover, the observed Firefox computed duration was already 2 s before the masked mutation while applied duration was 1 s: the update prose cannot simply be treated as a witnessed computed-property-change algorithm. Selecting and invalidating the timing input is the remaining bridge, even though the final input interpretations agree.
5. [Web Animations model liveness](https://drafts.csswg.org/web-animations-1/#model-liveness) begins with this normative requirement:

   > Changes made to any part of the model cause the entire timing model to be updated and any dependent style.

   The retained primary HTML places the subsequent immediate-update and computed-style examples inside `div.informative-bg`. Those examples explain the requirement; they are not additional algorithm calls that close step 4.
6. **Conditional downstream calculation:** once iteration duration is 2000 ms, [active time](https://drafts.csswg.org/web-animations-1/#calculating-the-active-time) is 750 ms in the active phase. [Overall progress, steps 2–3](https://drafts.csswg.org/web-animations-1/#calculating-the-overall-progress) divides active time by nonzero duration and adds the zero iteration start, giving .375. [Simple progress](https://drafts.csswg.org/web-animations-1/#calculating-the-simple-iteration-progress) leaves this interior fraction unchanged; [normal direction](https://drafts.csswg.org/web-animations-1/#calculating-the-directed-progress) and [linear easing](https://drafts.csswg.org/web-animations-1/#calculating-the-transformed-progress) preserve it. The [keyframe effect-value algorithm](https://drafts.csswg.org/web-animations-1/#the-effect-value-of-a-keyframe-animation-effect) selects the two explicit opacity endpoints and interpolates at .375; [composition](https://drafts.csswg.org/web-animations-1/#applying-the-composited-result) applies that value to the cascade. No unresolved-time, zero-duration, missing-target, nonanimatable-property, empty-keyframe or endpoint-fill branch applies. [EffectTiming](https://drafts.csswg.org/web-animations-1/#the-effecttiming-dictionaries) maps duration to iteration duration; the [effect interface](https://drafts.csswg.org/web-animations-1/#the-animationeffect-interface) distinguishes specified from calculated timing queries.

## Route enumeration and rejected shortcuts

The indexed step graph has zero getter-to-pending-style routes and zero pending-style-to-iteration-duration routes at both depths 9 and 12, with no truncation reported. These requirements are substantially declarative prose; absence of step edges does not prove absence of a normative obligation. A separate timing-dependency search finds 28 paths from transformed to overall progress. Its guard references are not 28 runtime executions: resolved values bypass early returns, normal direction excludes alternate/reverse branches, and the finite interior fraction excludes infinity/end-fill branches.

| Proposed shortcut | Why it does not finish this trace |
| --- | --- |
| Apply pending-style requirements directly to the CSSOM getter | Its explicit interface scope is CSS Animations/Web Animations operations. |
| Treat the liveness getter example as an algorithm | Primary HTML marks that material informative. |
| Conclude no update is required from zero graph routes | Prose obligations are not all step-invocation edges; no abort step proves non-reachability. |
| Use changed animation names or restart the animation | Names and identities are retained; that is not this scenario. |
| Infer the initial timing-input policy from the final result | Final base and composed inputs coincide; the initial inputs do not. |

**Verdict: INCONCLUSIVE** for the requested complete normative first-getter invocation chain. The final 2 s/.375 expectation has explicit value correspondence, arithmetic and dependent-style support, and animation-API pending-style requirements strengthen the later stale-timing observation. The missing piece is a traced CSS timing-input selection/invalidation and update boundary before CSSOM returns. This is not a conclusion that the specifications permit stale timing, nor a claim that initial same-element policy is settled. A normative cross-spec processing bridge or clarified timing-input/update rule would resolve the remaining trace gap.
